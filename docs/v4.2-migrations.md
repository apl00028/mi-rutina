# GymOS v4.2 — Migraciones

Las migraciones se ejecutan después de resolver el propietario y cargar o asignar su vault. Nunca se ejecutan durante la carga pública previa a autenticación.

## Orden

1. Migración de rutina/sesiones y drafts.
2. Modelo de perfil.
3. Adaptación del configurador histórico.
4. Dominio y biblioteca de ejercicios.
5. Estado de propuestas.
6. Estado de activaciones.
7. Sanitización del registro técnico de sincronización.
8. Guardado del vault y renderizado privado.

Cada frontera valida de nuevo el propietario. Un error restaura los valores raw capturados antes del arranque privado.

## Rutina legacy

La migración convierte A/B/C existentes en sesiones canónicas con IDs proporcionados y estables. Conserva huecos, metadatos desconocidos, prescripción y asociación mediante `legacySessionKey`. No fabrica sesiones vacías ni genera D/E/F. Una rutina ya canónica no se remigra.

Los drafts A/B/C se asocian a su `sessionId`. Los corruptos, extranjeros o sin sesión se conservan como huérfanos recuperables y no se cargan como entrenamiento activo.

## Snapshots

El snapshot previo a migración se construye desde una lista explícita de claves funcionales. No contiene vaults, otros snapshots, credenciales, sesión, configuración de Supabase ni datos de otro propietario. Las claves internas se eliminan solo al borrar todos los datos locales de su propietario o en la eliminación completa de su cuenta.

## Idempotencia

Repetir arranque, restauración o aplicación del mismo payload no debe cambiar IDs, orden, timestamps, revisión ni contenido normalizado. Rutina e historial mantienen igualdad JSON exacta durante migraciones que no los transforman.

Las constantes históricas de esquema y migración se conservan. `4.2.0-rc.1` identifica la aplicación y el formato de nuevas copias, no reescribe marcadores ya desplegados.
