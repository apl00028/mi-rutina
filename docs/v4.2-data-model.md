# GymOS v4.2 — Modelo de datos

## Propietario y vault

El propietario válido es el UUID del usuario autenticado o el identificador interno explícito `local` cuando el modo local está permitido. Los datos funcionales usan nombres de clave estables y se capturan dentro de `gymos:userVault:<ownerId>`. Al cambiar de cuenta se guarda el vault saliente, se limpian datos activos y estado de interfaz, y se carga el vault entrante.

Los snapshots internos de migración no forman parte de backup, sincronización ni captura funcional. Sus nombres usan un identificador opaco derivado del propietario cuando corresponde.

## Entidades principales

- Perfil: identidad de onboarding, objetivos, estados vitales, fase, disponibilidad, preferencias, ciclos e historial de cambios.
- Rutina canónica: `routineId`, `ownerId`, `revision`, metadatos y entre dos y seis sesiones.
- Sesión: `sessionId`, `order`, etiqueta/nombre/enfoque, duración y ejercicios prescritos. `legacySessionKey` solo asocia A/B/C históricos.
- Borradores: contenedor por rutina con `draftsBySessionId`; cada draft conserva identidad, propietario, revisión y `sessionDefinitionHash`.
- Historial: entrenamiento completado con identidad de rutina/sesión, snapshot del ejercicio realizado y compatibilidad legacy cuando existe.
- Biblioteca: ejercicios integrados y personalizados, favoritos, aliases, equipamiento, estado `archived`/`needs_review` y metadatos de dominio.
- Propuestas: contenido inmutable, baseline, comparación y lifecycle. Máximo 20 por propietario.
- Activaciones: baseline, target, estado de activación/rollback y snapshot transaccional. Máximo 10 por propietario.
- Seguimiento: medidas corporales, nutrición, salud, recuperación y análisis de entrenamiento.

## Claves canónicas de sesión

- `gymos:routine:canonical`
- `gymos:routineDrafts`
- `gymos:selectedSessionId`
- `gymos:sessionModelMigration`

Las claves `gymos:routine`, `gymos:draft:A`, `gymos:draft:B`, `gymos:draft:C` y `gymos:selectedSession` se mantienen como compatibilidad heredada. No existen `sessionD`, `sessionE`, `sessionF` ni claves draft D/E/F.

## Sincronización y backup

El payload incluye rutina canónica, drafts, selección, historial, perfil, biblioteca, propuestas y activaciones validadas del propietario. Excluye vaults, credenciales, sesión Auth, configuración secreta, archivos temporales y snapshots internos de migración.

Los archivos de rutina contienen prescripción, no resultados, cargas realizadas ni estado de entrenamiento. Los planes nutricionales profesionales conservan su origen histórico y nunca sustituyen automáticamente el objetivo actual.

## Contraseñas

Las contraseñas solo se envían a `supabase.auth.updateUser`. No se guardan en `localStorage`, vault, base de datos ni logs.
